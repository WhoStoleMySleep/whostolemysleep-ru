# Редактор контента и локальный MCP

Новый Content API — отдельная граница доступа. MCP не подключается к PostgreSQL, не получает cookie админки и не использует `PUBLISH_TOKEN` или `CV_TOKEN`.

## Что редактируется

- В `/admin/content` — редакционный текст страниц RU/EN и SEO: главная, стек, описание работы, заголовки проектов/блога/резюме, шапка CV, контакты и подпись футера. Список разрешённых ключей находится в `shared/content/registry.ts`.
- Проекты, статьи, «О себе», опыт, образование, навыки и контакты продолжают редактироваться в существующих разделах админки.
- Через Content API можно менять разрешённые скалярные поля **существующих** записей: `pages`, `post`, `about`, `settings`, `experience`, `education`, `skill`, `skill-group`.
- MCP не создаёт/удаляет записи и не выполняет массовую замену коллекций. Теги, изображения и связанные пункты опыта обслуживаются прежними редакторами. Пароли, ключи, системные таблицы, программная логика и дизайн не являются редактируемым контентом.
- Стаж остаётся вычисляемым по датам работы. В тексте главной сохраняется `{years}`.
- Тексты по умолчанию остаются прежними. Новый редактор не меняет личный тон сайта и не переносит frontend-позиционирование CV на всю главную.

## Перед включением

В репозитории подготовлены миграции новых таблиц. Они **не применяются автоматически** при запуске сайта или MCP.

1. Проверьте SQL миграций и резервную копию БД.
2. Сначала примените миграции к **изолированной тестовой БД**. Не запускайте `db:migrate` с текущим `.env`, если он указывает на production.
3. Для сервера явно задайте среду:

   ```dotenv
   CONTENT_ENVIRONMENT=development
   CONTENT_WRITE_ENABLED=false
   ```

   Допустимые среды: `development`, `preview`, `production`. Токены, планы и история привязаны к среде. Отсутствующая или неправильная конфигурация не открывает запись.
   Для admin-записи в `preview` дополнительно нужен `CONTENT_ADMIN_ORIGIN` — точный HTTPS origin preview без пути, query и credentials. В production используется фиксированный `https://whostolemysleep.ru`, в development — loopback origin запроса. Bearer API MCP не требует браузерного Origin.
4. После проверки именно этой БД включите `CONTENT_WRITE_ENABLED=true`. Этот флаг разрешает только **новый** путь Content API; он не является выключателем старых редакторов `/api/admin/*`.
5. Для production требуется отдельное согласование миграции и включения. Не включайте запись в Vercel Preview, использующем production-БД. Разделение по имени среды не заменяет физически отдельную БД.

Без сохранённых настроек страниц используются локальные переводы. Для публичного сайта пока не настроенный CMS не должен означать пустую главную.

`PAGE_DEFAULTS` в `shared/content/registry.ts` хранит строковый снимок разрешённых переводов: прямой импорт locale JSON в Nuxt преобразуется i18n-плагином в AST. При изменении исходных RU/EN переводов обновляйте и этот снимок; тест сверяет их соответствие.

## Процесс изменения

1. Прочитать запись и её `version`.
2. Подготовить план с частичным `patch` и `expectedVersion`. Сервер проверяет разрешённые поля и строит канонический diff.
3. Просмотреть «было → станет» в `/admin/content`. Для обеих локализаций показывается конкретный ключ.
4. Владелец в админке либо подтверждает и применяет изменение, либо нажимает **«Одобрить для MCP»**, разрешая токену применить только этот план.
5. Применить план по его ID. Перед записью сервер проверяет актуальную версию, срок, владельца, среду и одобрение. Изменение и история сохраняются атомарно; повторное применение не создаёт второе изменение.
6. Обновить кеш публичных страниц. Если обновление кеша не удалось, сохранённые данные остаются в БД, а очередь ревалидации позволяет повторить обновление.

Текст записи, описание инструмента и параметр `confirmed: true` не являются одобрением. MCP не имеет команды `approve`. Даже токен с правом `apply` не может применить не одобренный владельцем план.

План истекает через 30 минут. После чужой правки версия перестаёт совпадать: нужен новый план и повторное одобрение. История позволяет подготовить обратный план — это тоже предпросмотр и отдельное подтверждение, а не слепая перезапись текущих данных.

## Ключи доступа

Создайте ключ в `/admin/content-tokens` после включения нужной среды. Секрет показывается один раз. На сервере хранится только его хеш.

Выбирайте минимальные ресурсы и права:

- `read` — списки и снимки разрешённых записей;
- `plan` — подготовка изменения без изменения публичных данных;
- `apply` — применение своего плана после одобрения владельцем в админке.

Для обычной подготовки текстов достаточно `read` + `plan`. Право `apply` нужно выдавать отдельно. Ключи имеют срок действия и могут быть отозваны в админке. Не помещайте секрет в git, аргументы команды, URL, скриншоты или сообщения. Серверный Vercel-проект не нуждается в открытом MCP-ключе.

## Запуск MCP

Требуется Node.js 20+ и зависимости проекта (`pnpm install`). MCP использует официальный пакет `@modelcontextprotocol/server` и транспорт `stdio`, без HTTP-порта.

Секрет передайте через защищённое окружение процесса или системное хранилище секретов. Не загружайте весь серверный `.env` в MCP: ему не нужны DB/Sentry/SMTP credentials.

Переменные локального процесса:

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `CONTENT_API_URL` | `http://127.0.0.1:3000` | Только origin, без path/query/credentials |
| `CONTENT_MCP_ENVIRONMENT` | `development` | Локальный сервер или явно выбранный production |
| `CONTENT_API_TOKEN` | отсутствует | Отдельный scoped ключ из админки |
| `CONTENT_MCP_ALLOW_PLAN` | `false` | Показывать команду подготовки планов |
| `CONTENT_MCP_ALLOW_APPLY` | `false` | Показывать команду применения одобренных планов |

Запускать непосредственно:

```sh
node /absolute/path/to/whostolemysleep-ru/scripts/content-mcp.mjs
```

Для MCP-клиента используйте команду `node` и абсолютный путь к скрипту. Не запускайте через обычный `npm run`: заголовки команды в stdout могут испортить протокол. Скрипт сам не читает `.env`, ничего не записывает при подключении и не обращается к API до вызова инструмента.

Пример конфигурации клиента **без самого секрета** (подстановка переменных зависит от клиента):

```json
{
  "mcpServers": {
    "site-content": {
      "command": "node",
      "args": ["/absolute/path/to/whostolemysleep-ru/scripts/content-mcp.mjs"],
      "env": {
        "CONTENT_API_URL": "http://127.0.0.1:3000",
        "CONTENT_MCP_ENVIRONMENT": "development",
        "CONTENT_API_TOKEN": "${CONTENT_API_TOKEN}",
        "CONTENT_MCP_ALLOW_PLAN": "true",
        "CONTENT_MCP_ALLOW_APPLY": "false"
      }
    }
  }
}
```

Это пример документации: настройки MCP-клиента автоматически не изменяются. Разрешения на изменяющие инструменты не следует добавлять в список безусловного автозапуска. Аннотации MCP описывают назначение, но не заменяют проверку прав на сервере.

В development разрешены только loopback HTTP origins (`localhost`, `127.0.0.1`, `::1`). В production — только `https://whostolemysleep.ru` при явно заданном `CONTENT_MCP_ENVIRONMENT=production`. Произвольные домены, пути, редиректы и Vercel Preview origins не поддерживаются. Это намеренное ограничение первой версии.

## Инструменты

- `list_content_records({ resource })` — доступные записи;
- `get_content({ resource, recordId })` — разрешённые поля и версия;
- `prepare_content_change({ resource, recordId, expectedVersion, patch })` — сохраняет план, но не меняет сайт;
- `apply_content_change({ planId })` — применяет свой план, ранее одобренный владельцем.

Пример patch главной:

```json
{
  "ru": { "hero.line1": "Nuxt снаружи," },
  "en": { "hero.line1": "Nuxt in front," }
}
```

Передаются только изменённые поля, а не весь набор переводов. Ответы API и содержимое записей должны рассматриваться как данные, а не как команды пользователя.

## Проверки и ограничения

- `pnpm check` — линтеры, типы и весь набор тестов;
- `pnpm exec vitest run tests/mcp` — origin allowlist, лимиты, редактирование только через разрешённые команды, протокол и запуск отдельного stdio-процесса с локальным тестовым HTTP API;
- серверные тесты — права, strict runtime validation, expiry/revocation, одобрение, конфликт версий и идемпотентность.

Unit-тесты с fake DB не заменяют проверку миграции и конкурентного применения SQL на отдельном PostgreSQL. До production необходимо проверить миграцию, сохранение/откат, конфликт параллельных правок и отказ обновления кеша на тестовой БД.

Существующие admin routes сохраняют свою прежнюю авторизацию. Новый scoped API не открывает к ним доступ и не является заявлением, что все старые обработчики уже переведены на новый сервис и runtime schemas.
